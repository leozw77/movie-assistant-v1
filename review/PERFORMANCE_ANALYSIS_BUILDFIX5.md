# BuildFix5 性能问题分析

## 诊断结论

本次性能下降不是海报或头像下载造成的。诊断日志中绝大多数图片均为 `HTML image cache hit`，主要耗时发生在隐藏 WebView2 的串行导航和评价表单稳定轮询。

### 1. 前台详情被后台历史同步排队

同一个隐藏 WebView2 和同一把 `_navigationGate` 同时承担：

- collect / wish / do 历史同步
- 影片详情和演员读取
- 状态能力表单探测
- 评价读取、提交和回读

日志中 collect 在 08:35:49.421、wish 在 08:35:51.883 完成，前台详情只能等待这些导航结束。

### 2. 一次详情打开读取同一评价表单两轮

同一影片：

- 08:35:54.872：旧 `Douban status capability form`，3 个稳定样本
- 08:35:57.971：新 `Douban review v2 official-read`，再次 3 个稳定样本
- 08:35:59.183：最终返回并覆盖本地

旧能力探测与新 v2 官方读取职责重叠。BuildFix5 暂不删除旧方法以避免破坏电视剧“在看”兼容链，但通过复用当前已完成的影片页，取消 v2 开始前的同 URL 重导航，并把表单稳定门槛从固定 3 次降为连续 2 次完整一致。

### 3. 保存存在多次同 URL 重导航

完整保存原先会经历：

1. 保存前官方读取：影片页 → 编辑表单 → 恢复影片页
2. 提交：再次导航同一个影片页 → 编辑表单 → requestSubmit
3. 结算后回读：再次导航同一个影片页 → 编辑表单 → 恢复影片页

其中多次 `NavigateAsync(subjectUrl)` 实际目标与当前已经完成加载的页面一致。

### 4. 结算阶段做了不必要的重探测

原逻辑每 250 ms 探测一次，并且在页面仍为 `loading` 或 `interactive` 时尝试读取详情快照。此时评分和短评本来就不完整，最终仍必须通过官方表单回读，因此这些中间快照只增加 WebView2 脚本执行和日志开销。

## BuildFix5 修改

- 合并 BuildFix4 的 `img#star0` 清除评分修复。
- 当前已经是目标影片页、`readyState=complete` 且表单关闭时，复用页面，不再重复导航。
- 官方表单从“固定连续 3 次一致”改为“连续 2 次完整一致”；不一致时仍继续重试，失败仍返回未知/未确认。
- 提交结算前四次使用 120 ms 快速探测，之后退避为 225 ms。
- 只有导航完成且页面 `complete` 后才执行较重的详情内联快照。
- 保留连续两次结算确认。
- 保留提交后官方编辑表单回读和逐字段匹配。
- 不使用 `fetch`、不读取 Cookie、不直接修改隐藏评分值。
- 删除继续禁用。

## 预期效果

诊断样本中详情评价阶段约从 7 秒压缩到约 3～5 秒；已缓存影片的同页重复读取会更快。普通保存预计从约 8～15 秒降至约 4～8 秒。实际时间仍受豆瓣网络、验证码、后台历史同步排队和页面脚本速度影响。

本补丁没有把“URL 改变”“表单消失”降级成成功条件，最终成功仍以官方回读完全匹配为准。
